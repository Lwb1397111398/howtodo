# 应用自更新模块总览

## 模块职责（一句话）

让「工作如何做」App 自己发现并安装新版本：启动时静默检查 GitHub Release，发现新版弹窗，流式下载 APK 并唤起系统安装器覆盖安装；配合 GitHub Actions，推送代码到 main 后云端自动构建、自动发布到唯一的 `latest` Release。

## 运作流程（按数据流动顺序）

### 1. 云端出包（GitHub Actions）

- 触发：push 到 main（或手动 workflow_dispatch）→ `.github/workflows/build-release.yml`。
- 步骤：全量 checkout（`fetch-depth: 0`，版本号数提交要用历史）→ temurin JDK 17 → `android-actions/setup-android` → `gradle/actions/setup-gradle`（Gradle 8.9，仓库里**没有 gradlew**，CI 直接用装的 gradle 命令）→ `gradle assembleRelease` 出 release APK。
- 发布：把 `app-release.apk` 复制成**固定资产名** `howtodo-release.apk`（App 端按 `.apk` 结尾匹配，镜像直链也永远不变），用 `gh release` 滚动发布到 tag=`latest`：已存在就 `upload --clobber` + `edit --notes-file`，不存在就 `create`。
- 版本元数据：Release 说明**第一行**是 HTML 注释 `<!-- appupdate versionCode=8 versionName=0.1.8 -->`——GitHub 网页渲染不可见，只有 App 的正则解析它。
- 签名：release/debug 共用 `app/keystore/howtodo.jks`（口令默认 `howtodo`，可用环境变量 `HOWTODO_STORE_PASS`/`HOWTODO_KEY_PASS` 覆盖）。任何环境构建出的包签名指纹一致，才能互相覆盖安装。
- 版本号公式：`versionCode = git 提交数 + 4`，`versionName = "0.1.<提交数+4>"`（`app/build.gradle.kts` 里 `providers.exec { git rev-list --count HEAD }`）。偏移 4 是为了高于手工发布的 v0.1.0（=1）、v0.1.1（=2）；本机与 CI 对同一提交算出同一个号。

### 2. App 端检查（UpdateManager + UpdateChecker）

- 入口一：冷启动 `App.onCreate` → `updateManager.autoCheck()`，24 小时节流（SharedPreferences `update_prefs` 的 `last_check`），静默不打扰；用户点过「稍后」的版本（`skip_code`）不再弹。
- 入口二：设置 → 关于 → 「检查更新」→ `checkNow()`，不受节流，结果无论好坏都弹窗告知。
- 查询：GET `https://api.github.com/repos/Lwb1397111398/howtodo/releases/latest`，**必带 User-Agent**（缺了 GitHub 直接 403）。
- 多源轮换（防国内 DNS 污染）：直连 → `https://gh-proxy.com/`（2026-10-22 实测唯一还能透传 API 的镜像），逐源试，任一 200 即停；下载候选再补 gh-proxy.org / ghfast.top / ghproxy.net（三家都只透传下载，API 路径实测 403，不进查询链）。
- 令牌：**不需要**。仓库为公开仓库（2026-10-22 转公开），匿名 API 200、Release 资产可匿名下载，手机端零配置即可用。
- 解析比较：`UpdateParser` 先正则抓第一行元数据拿 versionCode/versionName，再从 assets 里找 `.apk` 结尾的资产取 `browser_download_url` 与 `size`；远端 versionCode > 本机 `BuildConfig.VERSION_CODE` 才算有更新。
- 错误文案全人话：403→限流换下一源；全部通道都 404→「云端暂无发布，等 CI 出新版」；网络连不上→「直连与镜像都失败」。

### 3. 下载安装（UpdateDownloader + UpdateInstaller）

- 弹窗展示新版本号、更新说明（元数据注释以下的正文）、包大小；点「下载」开始。
- 候选顺序：**查询成功的通道排第一**（DNS 污染是域名维度的，查询通下载大概率也通），再补直连/gh-proxy/ghfast.top/ghproxy.net（后两家只透传下载，所以不进查询链）。
- 流式下载 64KB 缓冲，先写 `update-<versionCode>.apk.part` → 校验实际字节数 == 预期大小 → 重命名进缓存 `cacheDir/updates/`；失败不留半截包。同版本完整包已存在则直接复用，不联网。
- 安装：`FileProvider`（authority `com.howtodo.fileprovider`，`file_paths.xml` 开了 `updates/` 缓存子目录）拿 content:// URI → `ACTION_INSTALL_PACKAGE` 唤起系统安装器。没开「安装未知应用」授权时跳系统开关页，开完回来再点一次。相同 versionCode 允许重装，更低会被系统拒绝。
- UI：`ui/update/UpdateDialogHost` 挂在设置页，由 `UpdateManager.state`（StateFlow）驱动六种状态弹窗：Checking/Available/Downloading（进度条百分比）/Downloaded/Failed/UpToDate。

## 入口文件清单

- `app/src/main/java/com/howtodo/update/UpdateConstants.kt` —— 仓库 owner/name 常量
- `app/src/main/java/com/howtodo/update/UpdateParser.kt` —— 纯 JVM 解析（元数据注释 + Release JSON）
- `app/src/main/java/com/howtodo/update/UpdateChecker.kt` —— 查询多源轮换 + `UpdateDownloader` 下载器
- `app/src/main/java/com/howtodo/update/UpdateInstaller.kt` —— FileProvider 唤起系统安装器
- `app/src/main/java/com/howtodo/update/UpdateManager.kt` —— 状态机 / 节流 / skip 版本
- `app/src/main/java/com/howtodo/update/UpdateModels.kt` —— UpdateInfo / UpdateUiState
- `app/src/main/java/com/howtodo/ui/update/UpdateDialogHost.kt` —— 六态 Compose 弹窗
- `.github/workflows/build-release.yml` —— CI 自动出包发版
- 接线改动：`App.kt`（autoCheck）、`di/AppContainer.kt`（updateManager 单例）、`ui/settings/SettingsScreen.kt`（检查更新入口 + 弹窗宿主）、`AndroidManifest.xml`（REQUEST_INSTALL_PACKAGES）、`res/xml/file_paths.xml`（updates 目录）、`app/build.gradle.kts`（版本号公式）、`settings.gradle.kts`（CI 跳过国内镜像）、`app/src/test/java/com/howtodo/update/UpdateParserTest.kt`（单测）

## 对外接口 / 被谁调用

- `AppContainer.updateManager`：被 `App.onCreate`（autoCheck）和 `SettingsScreen`（checkNow + UpdateDialogHost）调用。
- 本模块不被其他业务模块依赖；只向上依赖 `BuildConfig`、`util/Crypto`、Android 系统组件。

## 依赖的上游模块

- `di/AppContainer`：持有 UpdateManager 单例。
- `res/xml/file_paths.xml` + 清单 `com.howtodo.fileprovider`：安装授权读缓存 APK。

## 关键数据结构

- `UpdateInfo(versionCode, versionName, apkUrl, apkSize, notes, sourcePrefix)`
- `UpdateUiState`：Idle / Checking / Available / Downloading(percent) / Downloaded(file) / Failed / UpToDate
- SharedPreferences `update_prefs`：`last_check`、`skip_code`
- Release 元数据约定：说明第一行 `<!-- appupdate versionCode=N versionName=0.1.N -->`；资产固定名 `howtodo-release.apk`；tag 固定 `latest`

## 已知坑与约束

1. **User-Agent 必带**，否则 GitHub API 403。
2. **CI 的 checkout 必须 fetch-depth: 0**，浅克隆数错提交数 → 版本号算错。
3. **国内镜像透传能力会变**：2026-10-22 实测 gh-proxy.com 透传 API（200）；gh-proxy.org 已转 403（只剩下载透传候选）；ghfast.top/ghproxy.net 本就 403。镜像会倒闭/改规则，**每次改动前先 curl 验证**，别凭记忆。
4. **404 即「云端没发布」**：公开仓库匿名 404 只能是 latest Release 尚未创建（CI 首跑前/失败），不要写误导用户等令牌的话。
5. **引导死循环**：本模块的修复只对新版本生效。旧版（v0.1.1 及更早，没有更新入口）需一次性手动装新包：手机浏览器直接开镜像直链 `https://gh-proxy.com/https://github.com/Lwb1397111398/howtodo/releases/download/latest/howtodo-release.apk`（2026-10-22 实测 200、1.79MB、包内 versionCode=10 与元数据一致），下载覆盖安装一次，之后 App 内检查更新永远通得过。
6. **签名统一**：keystore `howtodo.jks` 随仓库提交（本仓库现已公开——与参照实现 Studying-with-friend 同样做法：个人项目接受「调试级钥匙公开」的权衡，恶意者能伪造同签名包，但**无法发布到本仓库 Release 渠道**，App 只认本仓库 latest）。口令默认 `howtodo`，可用 `HOWTODO_STORE_PASS`/`HOWTODO_KEY_PASS` 环境变量覆盖；换正式签名钥匙会断掉覆盖安装链路。
7. **settings.gradle.kts 按 CI 环境变量分流**：`System.getenv("CI")=="true"` 直连 google()/mavenCentral()（阿里云镜像在美区常 502）；本机仍走镜像。pluginManagement 的条件必须内联，不能引用文件级 val。
8. **仓库无 gradlew**，CI 用 setup-gradle 装 8.9 直接跑 `gradle`。
9. 未实测项（UNMEASURED）：真机端到端安装、国内手机 DNS 污染场景、CI 首次运行结果——推送后需过一遍验收清单。
