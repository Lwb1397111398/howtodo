# 工具模块总览

> 对应代码目录：`app/src/main/java/com/howtodo/util/`

## 模块职责

应用的基础设施层：私有目录存储布局与文件落地、备份导出与整库恢复、API Key 的系统密钥库加密、通用格式化。

## 运作流程（按数据流动顺序）

### 1. 材料落盘（util/Storage.kt）

所有材料原件一律以随机 id 命名存进 `filesDir/materials/<id>.bin`（中文原名只进数据库，规避路径编码与重名问题）。

- **外部文件**：`copyFromUri(uri, id)` 流式复制（64KB 缓冲）并同步算 SHA-256、查原始文件名与 MIME；单文件超过 **80MB**（`MAX_IMPORT_BYTES`）抛 `FileTooLargeException`，由调用方明确报错——旧版静默截断半个文件还报成功，是 2026-10-27 修掉的行为。返回 `null` 表示读取失败（流打不开/IO 异常），**异常与 null 是两种不同失败**，调用方都要接。
- **粘贴文本**：`writeText(id, text, name)` 直接落盘。
- **派生目录**：`raw_llm/`（每次 LLM 调用的完整报文，调试用，目前无清理上限）、`thumbs/`（缩略图）。

### 2. 备份与恢复（util/BackupManager.kt）

备份是这个 App 唯一的数据逃生通道，链路必须可靠：

- **导出**：先 `PRAGMA wal_checkpoint(FULL)` 把 Room WAL 日志里的最新写入并进主库文件（不做这步，当天数据可能不在备份里——旧版注释声称做了但实际没有，2026-10-27 修），再把 `howtodo.db` + 全部材料原件 + `backup.info` 版本标记打进用户选定位置的 zip。
- **恢复（两段式）**：
  1. `stageImport(uri)`：把 zip 解到 `filesDir/restore_staging/` 暂存目录（防 zip 路径穿越校验），校验备份里确实有数据库；此时运行中的数据库**完全不受影响**，失败只损失暂存目录。
  2. 调用方（SettingsScreen）`close()` 数据库 → `commitImport(staged)`：换库文件（rename 优先，失败降级 copy）、删残留 `-wal`/`-shm`、materials 目录**整目录替换**（备份里没有的旧文件全部清掉，不留孤儿）、清空 `thumbs/` 与 `raw_llm/` 派生缓存。
  3. `restartApp(context)`：拉起启动 Intent（NEW_TASK|CLEAR_TASK）后 `exit(0)` 杀进程——旧版 `finishAffinity` 只关界面不杀进程，后台协程可能拿着旧连接把刚换上的库改坏；现在换库与重启之间不留窗口。

### 3. API Key 加密（util/Crypto.kt）

AndroidKeyStore 里的 AES-256-GCM 密钥加解密供应商 API Key：随机 IV、密文连 IV 一起落数据库（只存密文）、解密失败返回 null（上游据此提示重新填写）。明文 Key 不出系统密钥库、不进备份。

### 4. 格式化（util/Format.kt）

时间 / 相对时间（「3 天后」）的中文格式化，界面与通知共用。

## 入口文件清单

- `util/Storage.kt`：私有目录布局、Uri 复制、SHA-256、文本落盘
- `util/BackupManager.kt`：checkpoint、导出、两段式恢复、进程重启
- `util/Crypto.kt`：API Key 加解密
- `util/Format.kt`：格式化

## 对外接口 / 被谁调用

- `Storage`：`di/AppContainer` 构造单例；`ImportManager`（导入落盘）、`IngestPipeline`（读原件）、`KnowledgeScreen`（图片抽取）、`SourceRepo.delete`（删原件）。
- `BackupManager`：`ui/settings/SettingsScreen.kt`（导出/恢复入口，构造需传 `AppDatabase` 做 checkpoint）。
- `Crypto`：`data/repo/ProviderRepo.kt`。

## 依赖的上游模块

`data/db`（BackupManager 需要 `AppDatabase` 执行 WAL checkpoint）；其余为纯 Android/JVM 能力，不依赖业务模块。

## 关键数据结构

- `Storage.Imported`：`file / sha256 / size / displayName / mime`。
- `BackupManager.Staged`：暂存目录 + 材料份数（内部类，两段式恢复的交接物）。
- `BackupManager.Result`：`ok / message`（人话结果，直接上屏）。
- `Storage.FileTooLargeException`：超 80MB 专用异常。

## 已知坑与约束

1. **恢复必须走全链**：stage → close → commit → restartApp，跳任何一步都可能让 Room 重新打开连接去覆盖/读写半换状态的库。
2. **备份 zip 无口令**：含全部聊天记录与材料明文（API Key 只有密文），导出位置由用户选，注意保管。
3. **raw_llm 有保留上限**：每次分析落一份完整报文，`writeRaw` 清理到只留最近 50 份（2026-10-27 起生效，此前无限增长）。
4. **80MB 是复制层的上限**：解析层还有自己的约束（PDF 15 页等），两处上限独立。

## 最后更新

2026-10-27：批次一修复——备份导出前真正执行 WAL checkpoint；恢复改两段式（暂存→关库→换库→自动重启进程）；恢复时整目录替换 materials 并清派生缓存；超 80MB 从静默截断改为明确报错。首次建立本总览。
