# 数据层模块总览

> 对应代码目录：`app/src/main/java/com/howtodo/data/`（`db/` 是表与查询，`repo/` 是业务仓库）

## 模块职责

用一个本地 Room 数据库（`howtodo.db`）承载全部业务数据，并把「表怎么读写」包装成各领域 Repo，供界面层与 AI 层调用；同时维护一张绕过 Room 的 FTS5 全文索引表，让检索不依赖联网。

## 运作流程

### 建库

- `AppDatabase.build(context)` 用 `Room.databaseBuilder(..., "howtodo.db")` 建库，注册 `FtsCallback()`。
- 数据库打开时回调里调 `FtsStore.ensure()`：尝试建 `chunk_fts` 与 `entity_fts` 两张 FTS5 虚拟表；失败的机型（部分国产 ROM 裁掉 FTS5）把 `FtsStore.mode` 降为 `LIKE`，检索改走 SQL `LIKE`。
- `App.onCreate()` 在 IO 线程先 `FtsStore.ensure()`，再做闹钟重建与未完成材料续跑。

### 表

| 表 | 实体 | 装什么 |
| --- | --- | --- |
| `provider` / `provider_model` / `role_binding` | `ProviderEntity` 等 | AI 供应商、模型清单、角色绑定（vision/reasoning/fast/chat） |
| `project` | `ProjectEntity` | 工作（标题、状态 ACTIVE/ARCHIVED、置顶、schemaRev、基线批次） |
| `source` | `SourceEntity` | 材料元数据（解析状态、错误原因、字符数、哈希、私有路径） |
| `chunk` | `ChunkEntity` | 材料切块正文与字符区间，检索命中的最小单位 |
| `batch` / `proposal` / `proposal_item` / `change_log` | 同名实体 | 每次 AI 分析的批次、待确认变更、逐条决策、可撤销日志 |
| `task` / `task_evidence` | `TaskEntity` 等 | 任务与「依据哪段材料推断」的证据行 |
| `knowledge` | `KnowledgeEntity` | 长期知识条目（跨工作复用） |
| `conversation` / `message` | 同名实体 | 聊天会话与消息 |
| `reminder` | `ReminderEntity` | 提醒与闹钟映射 |
| `import_queue` | `ImportQueueEntity` | 导入失败记录（如 Uri 读不到流） |
| `app_setting` | `AppSettingEntity` | 键值设置 |

两张不在 Room 里声明的表：`chunk_fts`、`entity_fts`（FTS5 虚拟表，`rowid` 对应 `chunk.id` / 知识条目 id）。

### 查询与视图

`Daos.kt` 放基础读写；`QueryDaos.kt` 放带 JOIN 的展示用视图：

- `SourceViewDao.observeAllWithProject()` / `observeForProject(projectId)`：材料 + 所属工作标题，Flow 订阅，材料状态一变界面自动刷新。
- `TaskViewDao.observeOpenWithProject()`、`ProposalViewDao.observePendingWithProject()`：今日页与工作页的待办/待确认列表。
- `ProbeDatabase.kt` 用于启动时的数据库可用性探测。

### 仓库层

| Repo | 职责 |
| --- | --- |
| `ProjectRepo` | 工作增删改查、归档/置顶、基线批次、`touch` 更新时间 |
| `SourceRepo`（同在 `ProjectRepo.kt`） | 材料读写、按哈希查重、改归属、改状态/指标、**删除级联**（FTS → chunk → 原件 → source） |
| `TaskRepo` | 任务状态流转、排序号、按工作订阅 |
| `ProposalRepo` | 生成提案、逐条决策、应用/撤销（撤销靠 `change_log` 回放） |
| `ProviderRepo` | 供应商与模型配置，API Key 经 `util/Crypto` 加密后落库 |
| `KnowledgeRepo` | 知识条目的增删查与按工作过滤 |
| `ChatRepo` | 会话与消息 |
| `ReminderRepo` | 提醒记录、过期清理、重排 |

## 入口文件清单

- `data/db/AppDatabase.kt`、`Entities.kt`、`Daos.kt`、`QueryDaos.kt`、`FtsStore.kt`、`ProbeDatabase.kt`
- `data/repo/ProjectRepo.kt`（含 `SourceRepo`）、`TaskRepo.kt`、`ProposalRepo.kt`、`ProviderRepo.kt`、`KnowledgeRepo.kt`、`ChatRepo.kt`、`ReminderRepo.kt`

## 对外接口 / 被谁调用

- 所有 Repo 由 `di/AppContainer` 构造并暴露为单例，界面通过 `context.container()` 取用。
- `SourceRepo.observeAll()` / `observeByProject()`：`MaterialsScreen`、`ProjectScreen`。
- `SourceRepo.delete(id)`：三个材料相关界面（材料库、工作页、预览页）删除确认后调用。
- `IngestPipeline` 直接写 `source` / `chunk` / `chunk_fts`（解析流水线）。
- `Retriever` 直接读 `chunk` + `chunk_fts`，命中后回表取正文与来源名。
- `ProposalRepo.apply()` / `undo()` 读写任务、知识、变更日志。

## 依赖的上游模块

无（最底层）。下游被 `ingest`、`ai`、`rag`、`ui`、`notify` 全部依赖。

## 关键数据结构

- `SourceWithProject`：`@Embedded SourceEntity + projectTitle`，材料列表直接用。
- `TaskWithProject`、`ProposalWithProject`：同理的展示视图。
- 状态常量对象：`SourceStatus`、`TaskStatus`、`ProposalState`、`ProjectStatus`、`SourceKind`、`SourceOrigin`。

## 已知坑与约束

1. **数据库版本 1，无迁移史**：改表结构必须补 Migration 或升版本，否则老用户升级会崩。
2. **FTS 表不归 Room 管**：写索引/删索引都要手动调 `FtsStore`，漏调会留下搜得到但取不到正文的幽灵命中。
3. **删除顺序**：`SourceRepo.delete` 必须先删 FTS 行再删 chunk（FTS 行按 chunk.id 定位），已按此实现。
4. **FTS5 机型差异**：`mode` 一旦降级为 LIKE，本次进程内不会再尝试 FTS5；检索精度会下降。
5. **Room 查询必须回到主线程之外**：所有 DB 调用在界面层都包在 `withContext(Dispatchers.IO)` 或 Repo 的 suspend 函数里。
6. **`observeAll()` 是热 Flow**：材料状态变化会自动推到界面，不需要手动刷新列表；但读取原件（图片/PDF）仍需显式 IO。
