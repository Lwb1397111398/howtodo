# 材料导入模块总览

> 对应代码目录：`app/src/main/java/com/howtodo/ingest/`（配合 `data/repo` 里的 `SourceRepo`、`ui/materials`、`ui/project` 的界面入口）

## 模块职责

把用户从微信分享、相册、文件管理器、相机、粘贴框送进来的原始文件，变成「原件 + 可检索的文字分块」：原件落私有目录，文字切块写进 `chunk` 表，再建 bigram 倒排索引供检索和 AI 分析使用。

## 运作流程

### 第 1 步：收下文件（先复制，后入库）

两个入口都走 `ImportManager.importUris()`：

- `ShareActivity`：微信/QQ 长按文件 → 分享 → 选本应用，或文件管理器「用其他应用打开」。
- `ProjectScreen` 的导入弹窗：相册多选、文件管理器多选、拍照、粘贴文字（文字走 `importText()`）。

`importUris()` 先对每个 Uri 调 `Storage.copyFromUri()`，把字节立刻复制到应用私有目录 `filesDir/materials/<id>.bin`。**必须当场复制**：微信给的读权限是临时的，等后台再读往往已经失效。复制时同时算 SHA-256、记原始文件名与 MIME；单文件超 80MB 会抛 `FileTooLargeException`，`importUris` 接住后计为导入失败并写明原因——**不再静默截断半个文件当成功**（2026-10-27 修）。

复制成功后用 `SourceRepo.findByHash(projectId, sha256)` 去重：同内容已存在就删掉刚复制的副本、复用旧记录（必要时补上 projectId）。新文件则写一条 `SourceEntity`，`status = NEW`，原件路径统一是 `materials/<id>.bin`（中文原名只存数据库，避免路径编码问题）。

### 第 2 步：排队解析

`parseOne()`（导入后立即解析）与 `parsePending()`（每次 App 启动续上未完成项）都拿同一把 `Mutex` 串行执行，避免多路视觉模型请求同时打满内存和额度。单条记录进入 `IngestPipeline.ingest()` 后状态置为 `PARSING`。

### 第 3 步：按类型取文字

`ingest()` 按 `SourceEntity.kind` 分三路：

- **图片**（`SourceKind.IMAGE`）：`ImageIngest.prepare()` 压到适合模型的尺寸，交 `VisionOcr.transcribeSingle()` 调视觉模型转写。
- **PDF**（`SourceKind.PDF`）：`IngestPipeline.transcribePdf()` 拿 `PdfIngest.Pager` **流式渲染**——渲染一批（3 页）就交 `VisionOcr.transcribeBatch()` 转写一批，prepared 用完即弃，内存峰值只驻留一批而不是全部页；加密或损坏导致一页都渲染不出时明确报错。每页正文由转写器拼上「【第N页】」标记（N = 真实页号）；某几页识别失败时**失败的页不进正文**，明细收集进失败清单。超过 `pdfMaxPages`（默认 15）时记「PDF 共 N 页，仅识别前 M 页」。
- **其余文档**（Word / Excel / PPT / RTF / ODT / TXT / 网页）：走 `DocumentExtract.extract()`。这里**不信扩展名，只认文件头**：
  - ZIP 容器 → 看内部条目判断 `word/document.xml`（docx）、`xl/workbook.xml`（xlsx）、`ppt/presentation.xml`（pptx）、`content.xml`（ODF）；
  - OLE 容器（老 .doc/.xls/.ppt）→ `CfbReader` 读流，遇到 `EncryptedPackage` 直接提示「设了打开密码」；
  - RTF → `RtfReader.read()`；HTML → 去标签取正文；纯文本按 BOM/可打印比例判断编码。
  - 因此「后缀是 .doc 实际是网页」「微信改过后缀的 docx」都能正确解析，不支持的格式会给出中文原因。

任何一步抛异常，都把原因截到 200 字写进 `source.error`，状态置 `FAILED`；没有读到文字、内容过短也分别落 `FAILED` 并写明原因。**视觉识别的部分失败**（某几页失败/超页截断）不整体失败：正文照常入库，失败明细写进 `source.error`（状态仍为 PARSED），预览页顶部展示「⚠ 部分内容未识别」横幅——2026-10-27 起不再把「（第N部分识别失败）」占位文本混进正文污染索引。

### 第 4 步：清洗、切块、建索引

拿到全文后 `cleanup()` 统一换行与空白，然后扫描正文里的「【第N页】」标记得到 (偏移, 页号) 列表，`Chunker.split(text, pageMarkers)` 切成带页码/字符区间的片段（PDF/PPT 的引用页码由此生效，2026-10-27 前该参数从未被传入、页码恒为空）。随后：

1. 先删除这份材料的旧 `chunk` 与旧 FTS 行（幂等，重复解析不会产生重复片段）；
2. 批量插入 `chunk` 表，`tokensEst` 由 `TokenBudget.estimate()` 估算；
3. 每块用 `Bigram.encode()` 生成 bigram 文本，写入 FTS5 虚拟表 `chunk_fts`；
4. 写字符数、token 数、页数、是否用过 OCR，`indexedAt` 打时间戳，状态置 `PARSED`。

部分国产 ROM 的 SQLite 裁掉了 FTS5，`FtsStore.ensure()` 启动时探测失败会降级为 LIKE 检索（`FtsStore.mode = LIKE`）。

### 第 5 步：重新解析与删除（2026-10-22 补齐）

- **重新解析**：`ImportManager.reparse(sourceId)` 不跳过已解析材料，先把状态打回 `NEW`、清空旧 `error`，再跑同一条 `ingest()`。界面入口有三处：材料库列表行、工作页材料列表行、材料预览页右上角「⋮」。解析中的材料不允许再触发，避免并发抢同一份文件。
- **删除**：`SourceRepo.delete(id)` 依次清理 ① FTS 行 ② `chunk` 行 ③ 私有目录原件 ④ `source` 行。FTS 行按 `chunk.id` 关联，必须趁 chunk 还在时先删，否则会留下指向已删材料的搜不到、删不掉的索引行。
- **解析中被删**：`IngestPipeline.ingest()` 在写 chunk 前会再查一次 `sourceDao.byId()`，材料已消失就直接中止，避免产生指向空 source 的孤儿片段。

## 对外接口 / 被谁调用

- `ImportManager.importUris(uris, projectId, origin, autoParse)`：`ShareActivity`、`ProjectScreen`。
- `ImportManager.importText(text, name, projectId)`：`ProjectScreen` 粘贴文字。
- `ImportManager.parseOne(ids, onProgress)` / `parsePending()` / `reparse(id, onProgress)`：`ProjectScreen`、`App`、两个材料列表与预览页。
- `IngestPipeline.ingest(sourceId, pdfMaxPages, onProgress)`：只由 `ImportManager` 调用。
- `SourceRepo.observeAll()` / `observeByProject()`：材料库页与工作页订阅状态变化（Flow 驱动界面刷新）。
- `SourceRepo.delete(id)`：材料库、工作页、预览页的删除确认之后调用；`ProjectRepo.delete` 级联删工作时会对其名下全部材料逐份执行同样的「FTS → chunk → 原件 → source」清理。

## 依赖的上游模块

- `data/db`：Room 的 `source` / `chunk` 表、`FtsStore` 虚拟表。
- `util/Storage`：私有目录布局、Uri 复制、SHA-256。
- `ai/AiRouter` → `VisionOcr`：图片与 PDF 的视觉转写（走用户配置的多模态模型）。
- `rag/Bigram`、`ai/TokenBudget`：索引编码与 token 估算。

## 关键数据结构

- `SourceEntity`：`id / projectId / displayName / mime / kind / localPath / sizeBytes / sha256 / origUri / origin / status / error / textChars / tokensEst / pageCount / ocrUsed / importedAt / indexedAt / batchId`。
- `SourceStatus`：`NEW → PARSING → PARSED`，失败为 `FAILED`（携带 `error`）。
- `ChunkEntity`：`id / sourceId / projectId / ord / pageNo / section / text / charStart / charEnd / kind / tokensEst`。
- `chunk_fts`：FTS5 表，`rowid = chunk.id`，正文是 bigram 串。

## 已知坑与约束

1. **分享 Uri 的权限是临时的**：必须 `importUris` 里同步复制完再返回，任何「稍后再读」都会失败。
2. **扩展名不可信**：材料统一存 `.bin`，格式判断只能看魔数；新增格式支持要加到 `DocumentExtract` 而不是 `FileKinds` 了事。
3. **PDF 默认最多识别 15 页**：`ingest(pdfMaxPages = 15)`；超页不再静默——失败明细与预览页横幅都会写明「共 N 页，仅识别前 M 页」。需要时可传更大值。
4. **视觉模型按页计费、耗时长**：图片/PDF 解析是这条链路里最贵的一步，失败重试会再花一次。
5. **FTS5 可能被裁**：`FtsStore.mode` 降级为 LIKE 后检索精度下降，但功能不中断。
6. **删除顺序不能改**：FTS 行依赖 `chunk` 行存在才能定位，顺序反了就漏删索引。
7. **`parsePending()` 只重试 `NEW`**：`FAILED` 不会在启动时自动重试，避免每次开 App 都重复烧视觉额度；失败材料由用户点「重试解析」手动触发。
8. **同内容去重按 `(projectId, sha256)`**：同一份文件导入到不同工作会各存一份，这是有意设计（工作内检索互不串味）。
