# 依赖容器模块总览

> 对应代码：`app/src/main/java/com/howtodo/di/AppContainer.kt`（含 `AnalysisState`）、`ui/common/Di.kt`

## 模块职责

手写依赖容器：应用启动时把数据库、存储、全部 Repo、AI 客户端、导入/分析/更新服务按依赖顺序构造一遍，集中暴露为单例，界面层经 `context.container()` 取用。不用 Hilt——依赖总共十几个，手写更透明，也省注解处理器拖慢构建。

## 运作流程

`App.onCreate()` 先 `AppContainer(context)`，构造顺序就是依赖顺序：

1. **基础设施**：`db`（Room，`AppDatabase.build`，含 v1→v2→v3 迁移与 FTS 回调）、`storage`（私有目录存储）。
2. **提醒链**：`reminderRepo`（提醒行生成）→ `alarmScheduler`（闹钟注册，依赖 reminderRepo）。
3. **工作/任务链**：`projectRepo(db, storage, alarmScheduler)`（删工作后要撤遗留闹钟）→ `sourceRepo` / `providerRepo` / `knowledgeRepo` / `chatRepo` → `taskRepo(db, reminderRepo, alarmScheduler)`（取消任务撤提醒、重开补排）→ `proposalRepo`。
4. **AI 链**：`llmClient`（单例 OkHttp）→ `router` → `vision` → `ingest` → `importManager` → `extraction`；`retriever` / `answerer` 供问答。
5. `updateManager`（自更新）、`appScope`（应用级协程作用域，SupervisorJob + IO，App 死了才取消）。

**后台分析状态机**：`_analysisState: StateFlow<AnalysisState?>`，`AnalysisState(projectId, message, proposalId?, error?)`。`startAnalysis()` 在 `appScope` 上跑 `extraction.analyze()`（离开页面不断），进度经 `update` 回写；`proposalId`/`error` 任一非空表示结束，界面消费后调 `dismissAnalysis()` 置空。已有分析在跑时再次调用被忽略。

## 入口文件清单

- `di/AppContainer.kt`：容器本体 + 后台分析状态
- `ui/common/Di.kt`：`Context.container()` 扩展（界面取容器的唯一入口）

## 对外接口 / 被谁调用

- 全部界面与 `App`/`MainActivity` 经 `container()` 拿单例；`AppNav` 不直接用。
- `startAnalysis(projectId, sourceIds)`：`ProjectScreen` 的「AI 分析」按钮。
- `analysisState`：`ProjectScreen` 订阅（进度弹窗 / 成功跳提案页 / 失败弹错误）。

## 依赖的上游模块

被所有模块依赖（最顶层组装者）；自身只依赖 `Application` 上下文。

## 关键数据结构

- `AnalysisState`：后台分析的可观察投影；null = 空闲。
- `appScope`：`CoroutineScope(SupervisorJob() + Dispatchers.IO)`，启动兜底任务（FtsStore.ensure、purgeOld、failStaleBatches、闹钟重建、续解析、检查更新）都挂它。

## 已知坑与约束

1. **构造顺序不能乱**：`taskRepo` 必须在 `reminderRepo`/`alarmScheduler` 之后，`projectRepo` 必须在 `alarmScheduler` 之后；编译器不管初始化顺序，乱序会在运行期拿到未初始化字段（Kotlin 属性无 lateinit 时按声明顺序执行）。
2. **后台分析同时只允许一个**：`startAnalysis` 有进行中检查，第二次调用静默忽略；换工作分析要等当前结束。
3. **appScope 是 IO 调度器**：挂上去的代码若要写 Compose 状态，必须 `withContext(Dispatchers.Main)`（MainActivity 踩过）。
