# 应用入口模块总览

> 对应代码：`App.kt`、`MainActivity.kt`、`ShareActivity.kt`

## 模块职责

进程的三个门口：`App` 负责启动初始化（建容器、通知渠道、每日早报计划、一批启动兜底任务）；`MainActivity` 承载全部 Compose 界面并处理通知点击跳转；`ShareActivity` 接收系统分享的文件/文本。

## 运作流程

### App.onCreate（启动兜底链）

1. `AppContainer(this)` 建容器 → `Notifications.ensureChannels()` 建三个通知渠道 → `DailyDigestWorker.ensureScheduled()` 保证每日早报计划存在。
2. 在 `container.appScope`（IO）上依次跑兜底（全部 `runCatching` 包住，单个失败不拖累其他）：
   - `FtsStore.ensure()`：确保 FTS5 虚拟表存在；
   - `reminderRepo.purgeOld()`：清 30 天前的过期提醒；
   - `importQueueDao().purgeDone(7 天前)`：清已处理完的导入队列记录（表只进不出会一直涨）；
   - `extraction.failStaleBatches()`：进程被杀时卡在 EXTRACTING 的批次置 FAILED，让用户能重新分析；
   - `alarmScheduler.rescheduleAll()`：重启/覆盖安装后按库重建全部闹钟；
   - `importManager.parsePending()`：上次没解析完的材料续跑；
   - `updateManager.autoCheck()`：静默检查应用更新。

### MainActivity（通知点击落工作）

`setContent { HowTodoTheme { AppNav(...) } }` 渲染全部界面。通知「今天截止：xxx」点击时带 `taskId` extra，`consumeIntent()` 查任务归属的工作后写 `startProjectId` 状态，`AppNav` 据此直接打开对应工作页；消费后回调置空。**`startProjectId` 的赋值在 `withContext(Dispatchers.Main)` 里做**——查询挂在 IO 调度器上，Compose 状态不能跨线程写。`onNewIntent` 处理应用已在前台时的新通知。

### ShareActivity（系统分享入口）

接收 `ACTION_SEND` 的文件/文本 Uri，第一时间经 `ImportManager.importUris` 拷进私有目录（分享来的 Uri 读权限是临时的），并入导入队列。

## 入口文件清单

- `App.kt`
- `MainActivity.kt`
- `ShareActivity.kt`

## 对外接口 / 被谁调用

- 三者都由系统拉起（Launcher / 通知 PendingIntent / 分享选择器），清单见 `AndroidManifest.xml`。
- `ReminderReceiver`/`BootReceiver`、`DailyDigestWorker` 依赖 `App.container` 单例，经 `(context.applicationContext as App).container` 取用。

## 依赖的上游模块

`di/AppContainer`（全部业务能力）、`notify`（渠道与调度）、`ui`（MainActivity 只挂 AppNav）。

## 关键数据结构

- `startProjectId: String?`（MainActivity 私有 Compose 状态）：待跳转的工作 id，消费即清。
- Manifest 里注册的组件：MainActivity、ShareActivity、ReminderReceiver、BootReceiver（**没有** DigestReceiver——每日早报只走 WorkManager，2026-10-27 删除了未注册的死接收器）。

## 已知坑与约束

1. **启动兜底全靠 runCatching**：任何一步抛异常都吞掉不崩，但也意味着失败无感知；排查问题看 logcat。
2. **consumeIntent 的 extra 要手动 remove**：不 remove 的话 `onNewIntent` 会重复消费同一个 taskId。
3. **appScope 里别直接写 UI 状态**：见「依赖容器模块总览」坑 3。
